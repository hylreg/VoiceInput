# 手机外部输入桥接设计

日期：2026-10-14

## 目标

用手机当 VoiceInput 的输入源：手机浏览器打开一条固定好记的地址，用手机自带输入法的语音键说话，
文字注入本机当前光标处。默认「说完自动发送」，也可以关掉开关回到手动点「发送」。

不改动现有「双击 Ctrl → 本机麦克风录音 → 注入」链路，两条路径并存，各由一个托盘开关控制。

## 为什么不走手机麦克风

不采集手机麦克风的音频，也不做 HTTPS。语音识别发生在手机键盘里，我们只传文字。
这消掉了 `getUserMedia` 必须 HTTPS、自签证书在手机上难装的整块成本。

代价：转写质量取决于手机输入法，不经过本机 ASR。这是用户明确要的方向。

## 架构

沿用项目现有的「常驻线程 + 共享状态 + 主循环轮询」模式，不引入新依赖（纯 std）：

```
手机浏览器 ──HTTP(局域网)──> 服务线程（TcpListener, 0.0.0.0:8765）
                                  │  SyncSender<BridgeRequest>
                                  ▼
                          主循环（现有 250ms 轮询，try_recv 排空）
                                  │  host.commit_text(text)
                                  ▼
                          LinuxInputMethodHost（xdotool 注入）
```

注入统一由主循环执行，理由是 `LinuxInputMethodHost` 只在主循环使用，集中一处可避免
手机注入与本机录音同时调 `xdotool` 抢焦点。这与现有 `LiveJobState` 单任务闸门同一思路。

## 请求流程

`POST /<口令>/send` 携带 `{ "text": "..." }`：

1. HTTP 线程从路径第一段取口令比对，不符直接 401；**鉴权在路由之前**，所以口令错时
   任何路径都是同一个 401，探测不出某个路径存不存在
2. 口令对，再校验开关状态，做文本归一化，然后送进有界队列
3. 主循环每轮 `try_recv` 排空队列，调 `commit_text` 注入
4. 结果通过请求内附的一次性 channel 回票（`mpsc::Sender<Result<(), String>>`）
5. HTTP 线程等回票，超时 2s 返回 503

注入延迟由主循环的 250ms 轮询周期决定，最坏 250ms，可接受。

`GET /<口令>/api/status` **不走主循环**。它读的两个值都是现成的共享状态，
HTTP 线程直接读：`mic_recording` 取 `LinuxMicAudioRecorder::is_recording()`
（recorder.rs:47，`LinuxMicAudioRecorder` 内部是 `Arc`，可 clone 进服务线程），
`bridge_enabled` 取共享的 `Arc<AtomicBool>`。这样状态查询不会被 30s 的录音周期阻塞。

## 接口

口令是 URL 路径的第一段，三个端点都挂在它下面：

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/<口令>` 或 `/<口令>/` | 返回内嵌页面 |
| `POST` | `/<口令>/send` | `{"text":"..."}` → 注入 |
| `GET` | `/<口令>/api/status` | `{"mic_recording":bool,"bridge_enabled":bool}` |

**路径即凭据**，不再有 `X-Auth-Token` 请求头这条通路。同一个秘密走两条路迟早会不一致，
而请求头还得靠页面脚本现拼——路径只要照着地址打就行。裸 `/` 的第一段是空串，
既不是合法口令也不会等于任何非空口令，因此也是 401。

路由按「口令段之后的剩余部分」判定（`GET ""` → 页面、`POST "send"` → 注入、
`GET "api/status"` → 状态）。方法不匹配视同 404，本服务不实现 405。

口令进 URL 路径的代价写在「地址与口令」一节。

`/api/status` 与 `/send` 的关键差别：**开关关闭时 `/api/status` 仍返回 200**
并如实报告 `bridge_enabled: false`，而不是返回 409。否则页面无法区分「开关关了」和「口令错了」。
409 只用于 `/send`。

### 状态码

下表除 401 外均针对 `POST /<口令>/send`；401 对三个端点都适用（口令不符一律 401）。

| 码 | 场景 |
|---|---|
| 200 | 注入成功 |
| 400 | 请求头无法解析、文本归一化后为空 |
| 401 | 口令段缺失或错误 |
| 404 | 口令正确但路径不在表里 |
| 409 | 手机输入开关已关闭 |
| 413 | 文本超过 500 字符 |
| 429 | 并发连接超过 8（或队列满） |
| 503 | 主循环 2s 内未回票（通常是在录音） |

### 响应体

`/send` 与 `/api/status` 一律返回 `application/json`：

- 成功：`{"ok":true}`
- 失败：`{"error":"<给用户看的中文说明>"}`

页面直接把 `error` 渲染到历史条目的红色提示里，不做状态码到文案的二次映射——
文案只有服务端一处来源，避免两边不一致。

## 文本归一化

注入前：**换行折叠为空格 → 连续空白折叠为单个空格 → 首尾 trim**。

手机 `textarea` 允许换行，`xdotool type` 会把 `\n` 发成回车——在聊天框里等于直接发出消息。
归一化后为空则拒绝，不注入。

## 剪贴板

`insert_text_into_active_window`（crates/voice-input-linux/src/ibus.rs:83）对非 ASCII 文本走
剪贴板粘贴路径。手机路径必须**沿用** `insert_indicator_and_save_clipboard`
（crates/voice-input-linux/src/ibus.rs:48）的保存-还原，否则用户正在复制的内容会被手机文字覆盖。

不插 `●` 指示符——用户在手机上，看不到本机光标处的指示符，插了反而是噪声。

## 托盘菜单

```
状态：已就绪
停止当前录音
───
本机麦克风：已启用        ← 点击切换
手机输入：已启用          ← 点击切换
───
复制外部输入地址
───
重启输入法
重启系统输入法
───
退出
```

开关用**纯文字项**，不用 `CheckmarkItem`。ksni 0.3.5 的 `CheckmarkItem` 会自行维护并翻转
`toggle_state`，若同时依据自己的 bool 渲染，菜单显示与实际状态会不同步。文字项自行渲染，
不可能不同步。

### 开关语义

两个开关独立，默认都开。

- **本机麦克风**关：双击 Ctrl 触发被忽略，每次触发打一行日志
- **手机输入**关：端口继续监听，`POST /send` 返回 409，页面显示「手机输入已关闭」

端口继续监听是刻意的——避免关一次开关就要在手机上重连。

「复制外部输入地址」在端口绑定失败时同样置灰（此时地址没有意义）。

### 持久化时机

内存态切换，**不即时写盘**；在已有的正常退出路径上（托盘退出 / 重启输入法）统一落盘一次。

理由：点一次开关就 fsync 一次 settings，对目录被 inotify 监视的场景会引发连锁反应；
主循环反正每轮读内存变量，写盘对生效无帮助。

副作用：被 SIGKILL 时开关丢失、回落默认（两个都开）。默认是安全方向，可接受。

### 复制地址

点击时**现算**主机名：配置里填了 `bridge_host` 就用它，否则现探测本机 IP，都没有则 `127.0.0.1`。

本机网卡是 DHCP 动态（`valid_lft` 会变），IP 会变。settings 只存端口、口令与用户显式指定的主机名，
**不存自动探测到的 IP**——存下来就是错的。

URL 组成：`http://<主机>:<端口>/<口令>/`，写进剪贴板。

主机名探测失败时回退到 `http://127.0.0.1:<端口>/<口令>/`，并打印一行提示。
这个地址在手机上打不开，但在本机浏览器里可以验证页面本身是否正常，
也是唯一的本机自测手段。

## 地址与口令

- **口令**：首次启动随生成一个三个音节（偶尔四个）的拼音词，存
  `~/.config/voice-input/linux-app.toml`
- **口令绝不进仓库**——它是机器级凭据，不属于 `config/voiceinput.env` 那类仓库级默认
- **IP 探测**：`UdpSocket::bind("0.0.0.0:0")` + `connect("192.0.2.1:80")` 读 `local_addr()`。
  UDP 不发包，纯 std，无新依赖
- **主机名**：`bridge_host` 配置项，空则回落 IP 探测。推荐填 Tailscale 的 MagicDNS 名字
- **端口**：默认 8765（实测空闲），可配 `--bridge-port`，进 settings
- **绑定**：`0.0.0.0`

绑 `0.0.0.0` 顺带覆盖 `tailscale0`（`100.65.179.39`），多一条不依赖同 Wi-Fi 的通路。
**但这同时意味着 tailnet 内其他机器也够得着**（tailnet 里有一台 Mac `air`），
口令是唯一屏障，不可视为装饰。

### 口令为什么是路径而不是 fragment

改这一版之前，口令放在 URL fragment（`http://10.10.10.42:8765/#k=<32 位十六进制>`）。
fragment 不进浏览器历史、不发 Referer，但换来的是**地址只能复制**：32 位随机串记不住、
打不出来，微信转发时 `#` 之后的部分还常被截掉；而 IP 是 DHCP 的，一变就得重发一遍。
用户的要求就是「固定地址 + 自己设的短口令」，所以口令改放路径第一段。

安全上的变化，如实记下：

| | fragment 版 | 路径版 |
|---|---|---|
| 进浏览器历史 | 否 | **是**（打开过就有记录，在用户自己手机上） |
| 发 Referer | 否 | **是**（同源，无第三方可收） |
| 明文传输 | 是 | 同网段明文；走 tailnet 时由 WireGuard 加密 |
| 可猜性 | 128 位随机 | **弱**（见下），靠 tailnet 设备鉴权 + 托盘开关兜底 |

不变的三条约束继续守：口令绝不进仓库；日志只记长度与结果、不记内容；配置文件 0600。
`tokens_match` 的常量时间比较保留——长度会立即返回，但长度本就写在地址里，泄漏长度无价值。

**默认口令的强度要说实话。** 音节表 24 项取三个 ≈ 1.37 万种，其中三个音节不足 8 个字下限的
128 种（`he`/`yu` 只有两个字）会补到第四个音节，合起来约 1.68 万种 ≈ **14 比特**，
**挡不住爆破**。真正的屏障是「必须先进 tailnet」外加托盘里的「手机输入」开关。
要更强就在配置里写一串随机字符（同一个字符集，32 位足够）。

口令只允许 8-32 位 ASCII `[A-Za-z0-9_-]`。非 ASCII 进路径要百分号编码，
出现 `/` 会直接把路由切断，卡死字符集就绕开了整类问题。归一化会 trim 并转小写。
旧版盘上的 32 位十六进制正好落在这个字符集里，升级时原样沿用，手机上存的地址不会失效。

## 页面

服务端 `include_str!` 嵌入的单个 HTML，无构建步骤、无外部资源。

**页面用相对地址发请求**：从 `location.pathname` 现算 `BASE`（末尾补斜杠，
好让 `/<口令>` 这种不带尾斜杠的写法也算对），再拼 `BASE + 'api/status'`、`BASE + 'send'`。
口令在路径里，所以换口令、换主机都不用改页面一行代码。

- `textarea` + 大号「发送」按钮（拇指够得着），viewport 适配，深色配色
- `textarea` autofocus
- **按钮发送与自动发送二选一**，页面上一行「说完自动发送」开关，默认开，状态存 `localStorage`
- **回车永不触发发送**——手机语音输入会插换行，回车当发送必然误触
- **首选信号是 `compositionend`**：手机输入法录完一段会发它，收到就立刻发送，不再等静默。
  手机键盘自己已经在判断「说完了」，用它比我们再猜一遍准且快
- **`compositionend` 后固定再等 50ms**（`SETTLE_MS`）才真正发。两种输入法都要这一下：
  有的先发 `compositionend` 再补发 `input`（那一刻 `textarea.value` 还是旧的，立刻读会读到空），
  有的一句话拆成几次 composition（中间那次 `compositionend` 之后几十毫秒就续上）
- **合成进行中（`compositionstart` 之后）一律不发**。合成期间输入法吐的是还没定稿的中间结果，
  此时「停笔」不代表说完，发出去就是半截话。`input` 事件说明还在继续吐字，不解除这道闩
- **`compositionend` 对手打中文也会发**，所以要靠 keydown 区分：手打必然伴随按键，
  语音插入不产生 keydown。合成期间见过 keydown 就退回停笔计时
- **兜底是 600ms 停笔**：个别输入法不合成、不发 `compositionend`，或用户纯手打时，
  仍靠 `input` 事件重置计时器、静默满 600ms 后发送
- **合成卡死看门狗 5s**：输入法开了合成却再也不结束（既不补 `input` 也不发 `compositionend`）时，
  停笔计时根本没机会武装。静默满 5s 就认定它卡住，解开闩让兜底接手。
  看门狗由每个 `input` 续期，所以一段正常的长语音不会被误判——语义是
  「合成中、且 5s 内一个 input 都没有」，不是「合成了 5s」
- **`input` 一律重置停笔计时**，所以改了字就不会发旧的。但**不动快路计时器**——
  有些输入法正是先发 `compositionend` 再补发这个 `input`，把它清掉就等于每次都白等 600ms
- **不留反悔窗口**：检测到输入完成就直接注入。要改就事后再改——注入的是文字，
  用户看得见，比多等 2s 划算
- **发送失败不自动重试**——否则遇到持续失败（本机录音中、口令失效）会变成死循环刷屏。
  失败后置「已停机」闩：那句没送出去的话还留在输入框里，再自动发会把下一句和它拼在一起
  注入
- **闩上之后必须把状态说清楚**。服务端文案常以「稍后重试」收尾，用户照着等就是无限期干等。
  所以失败提示要追加「自动发送已暂停」并给出**手机上做得到**的恢复动作：点「发送」重试
  （这条路径发成功即自动解开），或把「说完自动发送」关掉再打开。
  刻意**不**把语音继续输入当作解闩信号——闩的用意正是防「下一句和没发出去的那句拼接注入」，
  语音输入恰恰就是那个「下一句」
- **发送后清空输入框但保持焦点**，手机键盘不收起，可以连着说下一句。
  但只清空确实是我们刚发出去的那段——发送在途时用户可能已经在说下一句了
- 发送前先拉 `GET <BASE>api/status`：本机录音中直接提示「本机正在录音，稍后重试」并保留输入框内容，
  不干等 2s 超时（录音周期最长 30s）
- 发送结果追加到页面下方历史列表（时间戳 + 文字）；**失败条目标红并留在列表里**可重发
- 历史存 `localStorage`，刷新不丢。服务端**不存历史**，页面即全部状态
- 页面**不存口令**。口令就是当前地址，`BASE` 由 `location.pathname` 现算；
  `localStorage` 里只剩 `voiceinput.history` / `voiceinput.auto` 两项
- 收到 401 显示「口令已变更，请从托盘菜单重新复制地址」，展开粘贴框。新地址是**整页跳转**
  （口令在路径里，换口令等于换地址，只有重新加载才有意义），跳转前校验是 `http(s)://`
  开头且路径非空
- 路径缺口令段时（如裸 `/`）页面不会正常渲染：禁用发送与自动发送开关，
  提示「地址不完整，请用托盘菜单『复制外部输入地址』给出的完整链接打开」

## 降级与错误处理

- 端口被占用 / 绑定失败：**不影响主程序启动**，打警告，托盘「手机输入」项置灰
  （对齐现有 `SystemImeController::detect()` 的优雅降级写法）
- 请求体上限 500 字符。`xdotool type --delay 0` 仍逐字符走 X 协议，几百字明显卡顿；
  400-500 字符的手机端语音输入已属少见。超限返回 413 并回显实际长度
- socket 设 5s 读超时，避免半个连接占死线程
- 服务端最多 8 个并发连接；队列为 `sync_channel(8)`，满则 429
- 每连接一个线程，不做 keep-alive，用完即关
- **日志只记长度与结果，不记内容**——手机语音可能包含密码或私事，journal 是落盘的
- 口令不合法（手改配置写成带斜杠、或别的什么）时重新生成并打一行日志说明；
  空串是正常的首次启动，不视为异常
- 注入目标不确定是固有风险（焦点可能在终端、编辑器或已最小化的窗口），无法彻底解决；
  页面必须明确显示成功/失败，不允许静默成功

## 测试策略

沿用项目现有风格（纯函数单测 + 少量集成）：

- `bridge_addr`：口令生成满足自身的字符集与长度下限、归一化（大小写、字数边界、
  斜杠/非 ASCII/空格）、URL 形状
- `bridge_http`：请求行/头/Content-Length 解析、`split_prefix`（尾斜杠、深路径、裸根、
  缺前导斜杠）、路由、响应组装、归一化（换行、多空白、空串、超长）全部纯函数单测
- `bridge.rs`：测试内绑 0 端口跑真实 TCP 往返，覆盖 200 / 400 / 401 / 404 / 409 / 413 / 429 / 503
- 主循环排空逻辑：用测试内的假 host 断言注入文本与调用次数
- 页面侧：`/tmp` 里的 node 桩（假 DOM + 假 `setTimeout`）逐条跑自动发送状态机，
  另加「相对地址拼得对」一条
- CLI：`--bridge-port` 解析单测

**生成器的用例要跑遍组合空间，不能只抽一次。** 音节表里 `he`、`yu` 只有两个字，
三个凑起来可能只有 7 个字，短于下限（全空间 13824 种里占 128 种，约 0.93%）。
只抽一次的话大约每 115 次才撞上一回——靠抽样的用例是筛不出来的。
所以那条用例把 24³ 个组合全跑一遍（见「发现并修复的缺陷」）。

## 明确不做（YAGNI）

- 不做 HTTPS / 自签证书
- 不在手机上采集麦克风（改用手机键盘语音）
- 不做服务端历史
- 不做配对流程、不做多设备管理
- 不做文件/图片传输
- 不做手机端静音检测自动发送——手机键盘自己就在判断语音结束，用它发的事件即可，
  我们不必再猜一遍（见「页面」一节的 `compositionend`）
- 不做按 IP 限流——有口令 + 有界队列已足够，这是单个可信用户的服务
- 不做二维码（见下节）
- 托盘不做「重置口令」项——口令在配置文件里改一行就行，为它加一个对话框不值当

## 后续项：二维码

托盘画二维码供手机扫描，比手打 `http://leju.tail3e3e47.ts.net:8765/lanhexin/` 舒适得多。
口令改成路径之后这条的吸引力也降了：地址短到能记住，不再是必须复制粘贴的 32 位随机串。

本次不做，原因：本机既无 `qrencode`，也无 Python `qrcode`；crates.io 可达但需**新增
`qrcode` + `image` 两个依赖**。本仓库刚完成一轮「删约 2000 行、砍 optional 依赖」的瘦身，
加两个依赖换一个 onboarding 便利不划算。

它是纯加法（一个 `url_to_png_bytes` 纯函数 + 一个托盘项），不影响本设计，用着烦再补。

## 实测记录

2026-10-15，本机 `leju`（`10.10.10.42`），服务由 systemd 拉起。

### 本机 curl 用例（口令移入路径之后）

口令设为一个已知值，逐条打一遍。全部符合预期：

| 用例 | 结果 |
|---|---|
| `GET /<口令>/` | 200 `text/html`，17656 字节，与源文件字节一致，带 `Cache-Control: no-store` |
| `GET /<口令>`（无尾斜杠） | 200，同一个页面 |
| `GET /<口令>/api/status` | 200 `{"mic_recording":false,"bridge_enabled":true}` |
| `GET /`（裸根） | 401 |
| `GET /wrongpass/` | 401 |
| `GET /nope/more/path` | 401（第一段就是口令） |
| `GET /<口令>/nope` | 404（口令对、路径错） |
| `POST /<口令>/send`（空白文本） | 400 |
| `POST /<口令>/send`（501 字） | 413 |
| `POST /wrongpass/send` | 401 |
| `POST /<口令>/send`（10 字真实注入） | 200 `{"ok":true}` |

注入链路日志为「收到 N 字，等待注入」→「已注入 N 字」，注入内容在 journal 里出现 **0 次**，
口令在 4102 行 journal 里出现 **0 次**。剪贴板在注入后已还原，注入完成后无残留连接。

### 口令形态的升级路径

两边都实测过：

- **清空口令重启**：生成 10 位拼音口令，重启后保持不变（指纹一致），页面照常可用
- **写进带斜杠的口令**（`lan/hexin`）：被判非法，重新生成并打一行说明，服务正常起来
- **旧版 32 位十六进制口令**：落在合法字符集里，原样沿用，旧地址照旧 200——
  升级不会把所有手机的地址一次全废掉

### 页面侧（node 桩，假 DOM + 假定时器）

自动发送状态机共 4 个桩文件跑通：默认路径、手打走停笔、900ms 长句不被看门狗误判、
连续多句。失败路径单独跑：发送失败置闩且不拼发、闩上后不静默、
点「发送」重试与「关掉再打开开关」两条恢复路径都好使；401 展开粘贴框后停止自动发送、
非法地址拒绝跳转、合法地址整页跳转。

新增一条覆盖路径与相对地址的关系：页面在 `/<口令>/` 与 `/<口令>` 两种写法下，
请求都落到 `/<口令>/api/status` 与 `/<口令>/send`（差一个斜杠就会全 401）；
裸 `/` 时一次请求都不发，发送按钮与自动发送开关置灰，提示「地址不完整」。

### 端口占用降级

占住 8765 后启动：主程序照常运行（跑到超时才被杀），日志为

```
注入错误：桥接端口 8765 绑定失败：Address already in use (os error 98)
手机输入已禁用；本机麦克风不受影响
```

### 慢速请求头

25 行、每行间隔 200ms 的滴流请求头在 5s 处被切断并回 400——整条请求的截止时间生效，
不是逐次读超时（那样永远等不到上限）。

### 发现并修复的缺陷

**新生成的 token 从未落盘。** 盘上 `bridge_token` 恒为空串，而服务端拒绝空 token，
说明 token 只活在内存里：下次重启换一个，手机上存的地址全部失效。
根因是唯一的落盘点 `live_cli` 的 `save()` 跑在 `prepare_bridge` 之前，写下的还是空串，
`run_live_app` 之后再没有第二处。

修复：`BridgeSetup` 加 `token_is_new`，`run_live_app` 在启动时补写一次（仅在新生成时写，
避免每次启动都 fsync 配置目录）。实测清空 token 后连续重启两次，两次拿到同一串 32 位 token。

**页面被浏览器缓存。** 用户反馈「输入完成后仍要等约 2 秒才自动发送」，
但那个「N 秒后自动发送…」的文案早已从页面里删掉（源码与已编译二进制各 grep 计数均为 0）。
原因是响应既没有 `Cache-Control` 也没有 `ETag`/`Last-Modified`：手机浏览器拿的是
改动之前的旧页面，服务端换了几轮自动发送逻辑它都不知道。

修复：`HttpResponse::render()` 一律加 `Cache-Control: no-store`（页面本身只有 16KB，
省这点带宽毫无意义，代价却是手机上跑着一个和本机不一致的版本）。
加测试 `render_forbids_caching` 守住这条。**已缓存的旧副本要靠一次硬刷新清掉**——
之后自动发送的行为才与服务端一致。

**生成器会拼出「自己都不认」的口令。** 音节表里 `he`、`yu` 只有两个字，
三个音节凑起来可能只有 6-7 个字（`lanheyu`、`baihehe`），短于 `MIN_PASS_PHRASE_LEN = 8`
的下限。而 `generate_pass_phrase()` 原本固定只取三个音节。全空间 13824 种里
有 128 种落在这个坑里，约 0.93%——**约每 115 次生成撞上一回**。

这个缺陷原本是被 `bridge_setup_replaces_illegal_stored_pass_phrase` 以偶发失败的形式
暴露出来的（跑 30 次全套测试才挂一次）：它断言重新生成的口令 `normalize_pass_phrase`
认得，而生成器偶尔吐出一个自己都不认的。后果是下次启动 `prepare_bridge` 又判定非法、
再换一个，用户手机上刚存的地址白改。

修复：`phrase_from_bytes` 按音节累加，够 [`MIN_SYLLABLES`] 个音节**且**够
[`MIN_PASS_PHRASE_LEN`] 个字才停，凑不够就再加一个音节。生成空间从 13824 变成 16768 种
（≈ 2^14，与前面「口令强度说实话」那段的数字一致）。

**守住它的用例必须跑遍组合空间**：1080 次抽样才有约 99.98% 的把握撞上一次，
靠抽样等于留一颗定时炸弹。最终用例直接遍历 24³ 个组合断言全部合法；
把实现换回「取三个音节」会立刻挂在 `lanhehe` 上。

### 本机可达性摸底（关于固定主机名）
